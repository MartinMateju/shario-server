# Customer directory metrics

`GET /users` and `POST /users/filter` enrich the returned customer page with:

- `lastBookingAt`: ISO timestamp or null. The latest confirmed/completed reservation start at or before the read time, including ongoing visits. Future bookings, cancellations, draft/expired/failed holds and fully cancelled course places are excluded. Open-studio ownership uses `createdBy`; course ownership uses the customer's paid, processed order and remaining purchased places. The date respects the member's allowed locations and requires `bookings.view`.
- `totalSpentByCurrency`: sorted `{ currency, amountMinor }[]`, or null when unavailable. This is locally recorded cash paid on orders, linked voucher purchases and membership invoices, minus locally recorded successful cash refunds, including reconciled cumulative order and membership-invoice refunds. Cumulative refund summaries replace, rather than add to, specialized refund evidence; review/conflicting snapshots remain unavailable. Credit-pack purchases count; credit/voucher/membership-credit redemption does not count again. Wallet credit refunds are not cash refunds. A failed fulfillment does not erase a captured payment.
- `totalSpentCurrency`: the currency when there is one currency, or the validated tenant currency when there are no paid records. Multiple currencies return null. `totalSpent` is a compatibility major-unit scalar for CZK only, because older clients always label this field as CZK. Other currencies retain their authoritative array and currency but return a null scalar. No paid records returns an empty array and scalar 0 only when the tenant currency is CZK. Unknown monetary snapshots or conflicting refund evidence return null rather than a guessed total.

The complete spending summary requires all-location access and `orders.view`, `payments.view`, `vouchers.view` and `memberships.view`. A restricted member gets null, not a partial lifetime total or access to otherwise hidden financial records. Directory identity/filtering remains organization-wide; the active studio never changes these identity queries.

`GET /users/summary` supplies the authoritative `activeMemberships` count independently of directory search, pagination and the 2,000-customer list ceiling. It counts each customer once with an active or cancellation-scheduled, currently valid membership. Missing permissions, disabled membership module, insufficient report entitlement or uncertain entitlement dates return `null`. The `membershipScope` is `workspace` for unrestricted staff or `authorized_locations` for restricted staff. Shared all-location plans qualify for an authorized studio; a plan assigned to a different studio does not. Customer rows expose only an authorized active membership's name and status in `activeMembership`, while contracts and financial details remain in the membership API.

Queries are tenant-scoped and batched for the returned customer IDs. Booking dates use database aggregates; financial snapshots stream with bounded cursor batches. There are no per-customer reads, historical repair writes or provider calls. Voucher and invoice attribution requires an explicit customer ID; email matching is never used.

These figures summarize stored payment evidence, not a reconciliation of all external accounts. In particular, provider-dashboard changes and membership refunds/credit notes without local refund records cannot be reconstructed here. Do not replace missing amounts with current product prices, order gross totals, credit balances or inferred exchange rates.

## Paginated directory

The Customers screen uses these additive, `customers.view` protected routes. Existing `/users` and `/users/filter` consumers keep their contracts.

- `GET /users/directory?page=1&limit=10&search=&status=&membership=` returns `{data,totalCount,currentPage,pageSize,totalPages}`. Limits are integers from 1 through 50. Fixed tenant/customer/platform-role scope is applied before filtering. Without spending bounds, MongoDB sorts by `createdAt DESC, _id DESC`, selects the page, and only then calculates the booking/financial metrics above. Search remains an accent-folded full-name/contact/member-ID substring; literal regex characters are escaped. Active/invited/inactive status filters retain their legacy field fallbacks. Membership filtering uses current authorized `UserMembership` records, never stale membership labels on the customer document.
- `GET /users/directory/summary?timeZone=Europe/Prague` returns `{summary,membershipOptions,membershipAvailable,membershipScope,asOf,currency,spendingAvailable}` for the full, unfiltered customer directory. The client supplies its IANA timezone to retain browser-calendar month boundaries. Customer fields supply the customer/credit/date/status cards; the existing authoritative membership summary supplies the active count and visibility metadata. No lifetime orders, bookings, voucher purchases, membership invoices, or member-number repair is involved.
- `POST /users/directory/export` accepts directory filters or `{ids:[...]}`, never both. Selected IDs may additionally carry `spendFrom`, `spendTo` and `timeZone` solely as metric display context. It streams `{data:[...],totalCount,complete:true}` with backpressure. Every selected ID must be in the authenticated customer scope. Financial enrichment runs in batches of at most 100, without a 2,000-customer ceiling. The client must parse the complete response, verify its count and completion marker, and only then create a CSV. If a later batch fails or the connection closes, no successful completion marker is emitted. This is a live export, not a point-in-time backup: records use stable creation-time/identity ordering and ordinary customers created after traversal begins are excluded; concurrent updates/deletes can affect a filtered live export. A selected-record deletion aborts completion.

### Spending and current-credit filters

Directory reads and filtered exports accept `spendMin`, `spendMax`, `creditMin`, and `creditMax` in the validated workspace currency's **major units**. Bounds are inclusive and independently optional. Signed finite bounds are accepted; amounts with unsupported currency precision, unsafe minor-unit magnitudes, malformed/empty values, and reversed ranges are rejected. No foreign-exchange conversion is performed: unavailable, mixed-currency or other-currency spending cannot match a scalar bound. A customer with no payment history has known zero spending.

`spendFrom` and `spendTo` are independently optional strict `YYYY-MM-DD` calendar dates. `timeZone` is a validated IANA timezone, defaulting to `Europe/Prague`, as in the summary endpoint. Both boundary days are inclusive and respect timezone/DST calendar dates. The period means **payments made in this period, after their currently recorded cash refunds**, including refunds recorded later. It is neither a booking-date range nor a historical refund-event cash-flow report. Only confirmed `paidAt` evidence dates a payment; creation dates are never substitutes. Missing payment dates make a bounded-period result unavailable. Existing lifetime metrics remain alongside additive `periodSpentByCurrency` and `periodSpentCurrency` when dates are supplied; their array/null semantics match the lifetime fields. Dates alone change displayed metrics without excluding zero spenders or unavailable rows.

Spending bounds require all-location financial access (`orders.view`, `payments.view`, `vouchers.view`, `memberships.view`); unauthorized bounds fail with 403 instead of revealing matches. Dates alone retain rows and null unavailable financial metrics. Summary `spendingAvailable` reflects this complete permission/currency scope, and `currency` is the validated tenant currency or null. The summary remains unfiltered.

Current credits use the authoritative valid `moneyCreditsMinor` snapshot converted with the tenant currency exponent, falling back to a valid legacy balance. Missing/malformed balances stay null, never guessed zero; returned `moneyCredits` and summary credits use the same authority as filtering. Credit predicates run in MongoDB before count/pagination. Spending predicates necessarily examine financial evidence for every identity surviving the tenant/search/status/membership/credit predicates: the service streams candidates in stable creation-time/identity order, enriches at most 100 customer IDs at once, counts only matches, and retains only the requested page. It performs no per-customer queries, unbounded identity collection, writes, provider reads, or 2,000-customer cutoff. Filtered exports use the identical predicates and bounded batches; selected-ID exports retain their full scope/completion checks and reject amount filters. Unfiltered/dates-only reads still enrich only the page. Financial filtering is more expensive than a normal directory page because a correct global count requires examining candidate payment history; it is a live read, not a transactional snapshot.

The new read paths do not lazily assign missing member numbers. Creation/import remains responsible for those numbers; legacy records needing repair retain their existing identity fields until the explicit member-number migration is run. No customer repair writes occur on directory/summary/export reads.

Membership reads share reporting's module, plan, permission, tenant, location and entitlement-date predicates. Rows expose canonical `activeMembership` and `membershipAvailable`; `true` plus a null membership means no known active plan in the authorized scope. `false` means unavailable, so the client must not fall back to old user fields or label it as no membership. A known valid active membership retains precedence over an additional malformed candidate, matching the existing membership reader. Unknown-date candidates without a known active record remain unavailable and cannot match the `none` filter. The global count stays null if any scoped candidate has unknown dates; in that case facets are empty and the client disables/clears its membership filter. Otherwise facets describe each visible customer's latest active plan. Membership lookup runs after the page limit unless a membership filter requires it before pagination; exports retain bounded financial batches.

Native search normalization uses dynamic `$getField` (MongoDB 7.2+). Production MongoDB 8.0.37 was verified in the retained November 15 deployment metadata. Search runs one character traversal only when relevant non-ASCII characters require it; ordinary ASCII comparisons use native case conversion. This preserves Czech/Latin accents, decomposed accents, compatibility ligatures, fullwidth text and case-insensitive Greek sigma without server-side JavaScript. It does not claim a universal Unicode collation/linguistic search implementation.

### Index rollout

The schema adds `tenant_customer_directory_order` with keys `{tenant:1,tenantRole:1,createdAt:-1,_id:-1}`. Existing indexes stay intact. The application's connection does not override Mongoose auto-index creation, but deployment verification must confirm the named index actually exists; a schema declaration alone is not production evidence. If automatic creation is disabled, an authorized operator may create this single non-unique index explicitly:

```javascript
db.users.createIndex(
  { tenant: 1, tenantRole: 1, createdAt: -1, _id: -1 },
  { name: "tenant_customer_directory_order" },
);
```

Use `getIndexes()` to check its key order/options before creation. Do not run `syncIndexes`, drop, or rebuild unrelated indexes. The synthetic integration test verifies the first-page query uses this index without a blocking sort and examines only its ten returned customer documents. Filtered searches and total counts still need to examine matching customer identities. Only explicit spending bounds inspect off-page commerce history, in the bounded batches described above.

Also verify the non-unique `customer_membership_directory_lookup` index on the `usermemberships` collection, with keys `{tenant:1,user:1,status:1,startedAt:-1,_id:-1}`. The existing partial `isOpen:true` index is insufficient because reporting includes valid legacy records without that derived flag. Create only this missing index if necessary and authorized; do not alter the partial uniqueness constraint. The integration explain check verifies ten returned users inspect ten indexed membership records.

## Booking table companion changes

`POST /bookings/filter` already paginates in MongoDB before populating customer, product and location fields. The Bookings screen can use these page identities directly; loading the full customer directory merely for fallback names is unnecessary. The page response now projects table/export fields only, excludes internal booking arrays and delivery/access metadata, and matches each populated reference to the authenticated tenant. Missing or invalid related references remain null. Booking details and mutation endpoints are unchanged.

Sorting now includes `_id` as a deterministic tie-breaker in the same direction as the requested date field. The status filter accepts the stored booking states (`pending`, `processed`, `delivered`, `completed`, `cancelled`); payment filters accept `PENDING_PAYMENT`, `CONFIRMED`, `FAILED`, `EXPIRED`. Credit-funded and card-funded successful bookings both use `CONFIRMED`; refund evidence is stored separately and does not create a booking `REFUNDED` payment state. Unsupported filters are rejected rather than silently ignored. `summary.cancelledBookings`, like the existing today/payment counts, covers the complete filtered result before pagination and intersects the selected/authorized location and every active filter. These are filtered-result counts, not independent totals for other tabs. CSV export retains the client’s existing visible-page/selection behavior.

The Today view sends `dateScope: "today"`, resolved using the selected studio's timezone (or tenant/default timezone without a selected studio). Date-only `dateFrom`/`dateTo` values use that same local day's boundaries, including daylight-saving transitions; explicit ISO timestamps retain their exact instants. Invalid or reversed ranges are rejected. Member filters accept both `234` and `#234`; padded legacy identifiers such as `0234` remain distinct. The new lecturer dropdown sends `lecturerName` for literal snapshot-name equality; the older `lecturerId` lookup remains compatible, but the two cannot be combined.

`GET /bookings/filter-options?locationId=...` requires only `bookings.view` and returns `{products:[{_id,name,kind?}],lecturers:[{value,label}]}` from bookings within the trusted tenant/location scope. It includes historical and archived booked activities and has no 100-product catalog cutoff. Product lookups remain tenant-scoped; unbooked catalog entries, staff profiles, prices, customer identities and foreign references are not returned. Lecturer options are the stored booking names, so the filter also works after a lecturer's staff record is renamed or removed. The client loads these options only when the filters are opened.

Deployment should also verify the following two add-only booking indexes. They support the usual `start` sort with and without a single selected location; other sort/filter combinations and exact total counts may still examine more records. No production index change is performed by the regression tests.

```javascript
db.bookings.createIndex(
  { tenant: 1, location: 1, start: -1, _id: -1 },
  { name: "tenant_location_booking_directory_order" },
);
db.bookings.createIndex(
  { tenant: 1, start: -1, _id: -1 },
  { name: "tenant_booking_directory_order" },
);
```

Check existing key order/options with `getIndexes()` first and only create missing indexes when authorized. The 2,005-booking integration fixture checks far-page ordering, filtered counts, tenant/location boundaries and a ten-row indexed first-page read without a blocking sort. These synthetic checks establish bounded query behavior; they do not measure production response times.
